# Работа с данными

PostgreSQL через `pgx` (пул соединений), запросы собираются Squirrel, схема версионируется goose.

## Прозрачные транзакции

Транзакция живёт в контексте, а не в сигнатурах. Сценарий оборачивает несколько операций
в `txManager.Do(ctx, func(ctx) error { ... })`, репозиторий внутри достаёт соединение через
`r.getter.DefaultTrOrDB(ctx, r.pool)`.

Смысл: репозиторий не знает, работает он внутри транзакции или нет, и его не нужно
дублировать в двух вариантах. Объект транзакции не протаскивается через слои.

Следствие для логирования: бизнес-события пишутся **после** выхода из `Do`, а не внутри.
Внутри транзакция ещё может откатиться, и лог соврал бы про оплаченный заказ
(`order/internal/service/order/pay.go`, `cancel.go`).

## SELECT ... FOR UPDATE и порядок блокировок

Резервирование деталей конкурентно: несколько заказов одновременно уменьшают доступный
остаток одних и тех же строк. Защита — чтение под блокировкой внутри транзакции
(`inventory/internal/repository/part/list_for_update.go`), доступность считается как
`stock_quantity - reserved`.

**Порядок захвата блокировок обязан быть детерминированным.** В `buildListQuery`
(`inventory/internal/repository/part/query_parts.go`) ветка с фильтром по UUID добавляет
`ORDER BY uuid` именно для `FOR UPDATE`. Без сортировки Postgres блокирует строки в порядке
выдачи, и две транзакции, захватившие корпус и двигатель в разной последовательности,
встают в взаимную блокировку — в логах это `ERROR: deadlock detected`, наружу уходит 500.

На выдачу сортировка не влияет: `mapAndOrder` всё равно раскладывает результат в порядке
запрошенных UUID.

Проверяется это тестами конкурентности (`order/tests/concurrency_test.go`): два параллельных
заказа на последнюю единицу — один получает 201, второй 409.

## Пул соединений

`pgxpool.New` без параметров берёт дефолт `max(4, NumCPU)` — 4–8 соединений на весь сервис.
Для inventory этого мало: транзакция резервирования держит соединение всё время ожидания
блокировки строки, поэтому несколько параллельных резервирований выгребают пул досуха,
и даже быстрые чтения встают в очередь за свободным соединением.

Размер пула вынесен в конфиг: `inventory/internal/config/pg.go`, поле `MaxConns`
(`yaml:"max_conns"`, `env:"POSTGRES_MAX_CONNS"`), подставляется в DSN как `pool_max_conns`.
При неположительном значении параметр в DSN не добавляется: `pool_max_conns=0` pgx считает
ошибкой конфигурации.

## JSONB для свойств деталей

У разных типов деталей разные характеристики: у корпуса — `strength`, у двигателя — `class`
и `required_strength`, у щита — `shield_type`, у оружия — `weapon_type`. Всё это лежит
в одной JSONB-колонке `parts.properties` вместо таблицы на каждый тип.

Формат — паттерн Pointer Union: `{"<тип>": {<свойства>}}`, где ключ верхнего уровня
определяет тип свойств. `json.Unmarshal` заполняет ровно одно поле в `PartProperties`
(`inventory/internal/model/valueobject/part_properties.go` — ровно одно поле non-nil).
Десериализация живёт в слое хранилища (`inventory/internal/repository/record/part_properties.go`), домен
json-тегов не несёт.

`DEFAULT '{}'` — новые детали без свойств получают пустой объект, а не NULL.

## Миграции

goose, каталог на сервис: `migrations/<service>`. В контейнерном режиме их накатывает
одноразовый контейнер `migrator-<service>`, который стартует после healthcheck БД
и завершается с exit 0.

Сиды: `20260518174309_seed_parts.sql` — каталог деталей, `20260530121659_update_seed_properties.sql`
— их характеристики (значения подобраны так, чтобы алюминиевый корпус не тянул двигатель
класса B — это используется в тестах несовместимости), `20260530121706_increase_stock_quantity.sql`
— остатки под API-тесты. Плазменный корпус `…440007` намеренно с нулевым остатком: на нём
проверяется сценарий out-of-stock.

Фикстуры нагрузочного теста в миграциях **не** живут — см. [testing.md](testing.md).
