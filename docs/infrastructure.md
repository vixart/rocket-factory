# Инфраструктура: сборка и запуск

Оркестрация — [Task](https://taskfile.dev) (`Taskfile.yaml`), инфраструктура — Docker Compose,
разложенный по каталогам `deploy/compose/{core,observability,order,inventory,iam,services}`.

## Порядок подъёма

```
up-all
 ├─ net:create                       общая сеть microservices-net
 ├─ up-infra:parallel                ← четыре стека параллельно
 │   ├─ up-core                      Kafka + Redis + observability, kafka:init, es:init, jaeger:wait
 │   ├─ up-order                     postgres + миграции
 │   ├─ up-inventory                 postgres + миграции
 │   └─ up-iam                       postgres + redis + миграции
 ├─ docker compose up services       5 сервисов + nginx, order в 3 репликах
 └─ kibana:init                      ← последним
```

Почему именно так:

- **Стеки независимы**, им нужна только общая сеть. Task выполняет `deps` параллельно,
  поэтому холодный старт Elasticsearch перекрывается подъёмом баз, а не складывается с ним.
- **Сеть создаётся до параллельного этапа** — одновременное создание из четырёх задач было бы гонкой.
- **`docker network rm` убран из `up-core`.** Удаление сети из-под уже стартующих контейнеров
  ломает их подключение. Сеть удаляет только `down-core`.
- **`kibana:init` — последним шагом.** Kibana стартует ~40 секунд; если ждать её внутри
  `up-core`, это время встаёт в критический путь. В конце она уже прогрелась параллельно
  со всем остальным. По этой же причине `up-all` вызывает шаги `up-infra` по отдельности,
  а не целиком — иначе Kibana ждали бы до сборки сервисов.
- **Топики Kafka создаются до старта сервисов** — см. [kafka.md](kafka.md).

## Ускорение сборки

Три вещи, которые дали основной эффект (холодный `up-all`: 5m42s → ~1m41s).

**1. `.dockerignore`.** Контекст сборки — корень репозитория (`context: ../../..`), и он уезжает
демону на каждую из шести сборок. Без `.dockerignore` это ~294 МБ, из которых 289 МБ — `bin/`
с бинарниками инструментов разработки. Кроме объёма, это ломало кеш: переустановка любого
инструмента меняла контекст и инвалидировала `COPY . .` во всех образах сразу. С `.dockerignore`
контекст — 43 КБ.

**2. BuildKit cache mounts.** Кеш компиляции Go (`/root/.cache/go-build`) и модулей
(`/go/pkg/mod`) вынесены в cache mounts, а не живут в слое образа. Без этого каждая сборка
компилировала stdlib и все зависимости заново — это и были ~2 минуты на сервис. Кеш общий
между сборками, поэтому пятый сервис собирается почти мгновенно. Пересборка одного сервиса
после правки кода: 1m58s → 3.4s.

**3. Observability поднимается по контейнеру за раз с `--no-deps`.** Обычный `up --detach`
не возвращает управление, пока не выполнятся `depends_on: condition: service_healthy`,
то есть держит запуск Kibana до готовности Elasticsearch — ~55 секунд ожидания в foreground.
Kibana и коллектор переподключаются сами, поэтому дешевле запустить всё сразу, а готовности
дождаться отдельными шагами. Важно: `--no-deps` со **списком** сервисов не помогает —
зависимости внутри списка всё равно действуют, нужен отдельный вызов на сервис.

Дополнительно: у Elasticsearch зафиксирован heap (`ES_JAVA_OPTS=-Xms1g -Xmx1g`) и выключен ML —
53s → 37s до готовности.

## Healthcheck'и БД

`interval: 2s` + `start_period` вместо `interval: 10s`. На этой проверке ждёт `up --wait`,
а при десятисекундном интервале первая проверка происходит через 10 секунд после старта,
хотя postgres готов за 1–2. Один стек БД: 19.6s → 13.1s.

## Миграции контейнером

`docker compose run --rm -T --build migrator-<service>` — одноразовый контейнер goose,
возвращающий свой exit-код. `up --wait` на весь compose-файл **не годится**: он считает
завершившийся migrator упавшим, даже при exit 0.

## Вывод в терминал при параллельном запуске

Симптом: строки уезжают лесенкой вправо, вывод нечитаемый. Причина — терминал в raw-режиме
(выключен ONLCR), и всё, что печатается в это окно, идёт с `\n` без возврата каретки.

Два источника, оба — docker compose:

1. **tty-прогресс compose** перехватывает терминал. Лечится `--progress plain` — флаг
   ставится **всем** compose-вызовам, включая тот, что поднимает сервисы (он выполняется
   один, но его таблица прогресса ломала терминал для всего, что печаталось следом).
2. **`compose run`** выделяет контейнеру TTY и на время работы держит терминал в raw.
   Три мигратора идут параллельно, окно длинное, и в него попадает вывод соседних задач.
   Лечится флагом `-T` — goose в TTY не нуждается.

Плюс `silent: true` у задач с многострочными shell-блоками: Task по умолчанию печатает весь
скрипт целиком, и в параллельном выводе это третий источник каши.

Проверять такие вещи нужно под настоящим PTY (`script -qec "task up-all" out.raw`) — при
перенаправлении в файл compose сам переключается на plain, и проблема не воспроизводится.
Признак в записи PTY — переводы строки без CR.

## Nginx

`deploy/nginx/nginx.conf` — балансировщик перед репликами order-service. Количество реплик
в конфиге **не задаётся**: Docker DNS резолвит имя `order-service` в адреса всех реплик,
nginx раскидывает запросы round-robin. Число реплик определяется при запуске
(`--scale order-service=3`).

## Rate limiter

`platform/pkg/ratelimit/middleware.go` — HTTP middleware поверх `redis_rate`.

Алгоритм — GCRA (вариант token bucket), реализованный атомарно в Redis через Lua-скрипт.
Ключевое следствие: счётчик общий для всех реплик, поэтому лимит глобальный, а не
per-instance. При трёх репликах order за nginx `rate: 100` означает 100 rps на систему,
а не 300.

Отдельный Redis (`redis-ratelimit`), не тот, в котором лежат сессии IAM. Префикс к ключу
добавлять не нужно — `redis_rate` сам добавляет `rate:`.

Настройки в `order/config.docker.yaml` (`rate_limit.rate`, `rate_limit.burst`): `rate` —
средняя допустимая скорость, `burst` — размер разрешённого всплеска.

При нагрузочном прогоне именно этот лимит определяет потолок успешных заказов: всё сверх него
получает 429, и это ожидаемая картина, а не сбой.

## Redis-клиент: платформенные гарантии

`platform/pkg/redis/client.go` применяет настройки поверх переданных опций:

- `ContextTimeoutEnabled = true` — go-redis начинает уважать deadline контекста. Без этого
  команда может пережить отменённый запрос.
- Дефолтные таймауты, если вызывающий их не задал: dial 5s, read/write 3s.

Логгер принимается как `*slog.Logger` из стандартной библиотеки. Это сделано ради подмены
бэкенда: slog — стандартный фасад логирования в Go, при переходе на другой бэкенд достаточно
подменить `slog.Handler` при инициализации, сигнатуры потребителей не меняются.

## Ловушки, стоившие отладки

- **`cp` для git-хука.** Символическая ссылка не годится: хук остаётся невыполняемым файлом,
  а git молча пропускает такие хуки. Поэтому `hooks:install` копирует файл и делает `chmod +x`.
- **Порт Redis у IAM — 6380**, а не 6379: 6379 занят `redis-ratelimit`.
- **`set -e` в многострочных блоках Task.** Без него ненулевой код команды затирается
  финальным `echo`, и задача молча рапортует об успехе.
- **`LIKE` не работает по колонке типа `uuid`** в Postgres (`operator does not exist: uuid ~~ unknown`) —
  нужен явный список или приведение к тексту.
