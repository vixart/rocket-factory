# Архитектура кода

## Слои

```
API → Service → Repository
              → Client (внешние сервисы)
```

Направление зависимостей — сверху вниз, обратных импортов нет. Транспорт (HTTP/gRPC/Kafka)
знает про сценарий, сценарий про транспорт — нет.

## Три модели данных и конвертеры

Одна и та же сущность живёт в трёх видах, и это сделано намеренно:

| Модель | Где | Зачем отдельная |
|---|---|---|
| API-модель | сгенерирована из OpenAPI/proto | контракт наружу, меняется по своим правилам версионирования |
| Доменная модель | `<service>/internal/model` | бизнес-правила, ничего не знает про JSON и SQL |
| Модель хранилища | `<service>/internal/repository/record` | теги БД и JSON, форма таблицы |

Пример, почему их не сливают: `inventory/internal/repository/record/part_properties.go` —
структура для десериализации JSONB с json-тегами. Теги принадлежат слою хранилища,
а не домену; если бы домен нёс их на себе, изменение формата колонки тянуло бы за собой
изменение доменной модели.

Между слоями работают конвертеры (`<service>/internal/**/converter`).

## Инверсия зависимостей

Интерфейсы объявляет **потребитель**, а не реализация. В каждом сценарном пакете лежит
`deps.go` с описанием того, что этому сценарию нужно от мира:

- `order/internal/service/order/deps.go` — `Repository`, `InventoryClient`, `PaymentClient`,
  `OrderPaidProducer`, `TxManager`;
- `inventory/internal/service/application/part/deps.go` — `Repository`, `TxManager`.

Отсюда два следствия: реализацию можно подменить (в тестах — мок от mockery), и сервисный
слой не импортирует пакеты инфраструктуры.

## DI-контейнер

Ручной DI без библиотек: `<service>/internal/app/di.go` в каждом сервисе. Зависимости создаются
**лениво** — объект создаётся при первом обращении к геттеру и кэшируется в контейнере.
Смысл: сервису, который не дошёл до работы с БД, не нужен пул соединений.

## Порядок закрытия ресурсов

`platform/pkg/closer` — глобальный closer, функции закрытия вызываются в порядке **LIFO**:
последний зарегистрированный ресурс закрывается первым (`platform/pkg/closer/closer.go:70`).

Это не косметика. Ресурсы регистрируются в порядке создания: сначала БД, потом сервисы,
потом gRPC/HTTP-сервер. При завершении нужен обратный порядок: сначала остановить сервер
(перестать принимать запросы), дождаться завершения текущей бизнес-логики и только потом
закрывать соединения с БД. Если закрыть БД первой, обрабатывающиеся запросы упадут.

`CloseAll` безопасен для повторного вызова — выполняется один раз.

Глобальный экземпляр инициализируется при загрузке пакета, поэтому создавать closer вручную
не нужно — достаточно пакетных `closer.Add` / `closer.CloseAll`.

## Обработка ошибок

На каждом слое — свои ошибки-маркеры (`<service>/internal/errors`), наверх они идут обёрнутыми
через `%w`, а на границе транспорта разворачиваются в коды ответа.

- HTTP: `order/internal/api/order/v1/error_handler.go` — глобальный hook ogen
  (подключается через `orderv1.WithErrorHandler`). Маппинг: ошибки декодирования и валидации
  от ogen → 400, `ErrOrderNotFound` → 404, `ErrUnauthorized` → 401, конфликты статуса и
  остатка → 409, остальное → 500.
- gRPC: `inventory/internal/interceptor/error.go` и `iam/internal/interceptor/error.go` — доменные ошибки в `codes.*`.

Правило логирования, вытекающее отсюда: ошибку логирует тот, кто её превращает в ответ,
а не каждый слой по пути. Иначе одна ошибка попадает в лог трижды.

## Конфигурация

`cleanenv`: YAML-файл + переопределения из переменных окружения, приоритет у env.
Профили — отдельные файлы: `config.local.yaml`, `config.docker.yaml`, `config.staging.yaml`,
`config.production.yaml`; выбор через `CONFIG_PATH`.

Env-файлы разделены по способу запуска: `<service>/<service>.env` — для локального запуска
(адреса хостовые), `<service>/<service>.docker.env` — для контейнера (адреса внутри docker-сети),
`deploy/compose/<service>/compose.env` — переменные самого контейнера БД. Значения в них
должны совпадать, иначе локальный сервис пойдёт в другую базу, чем поднял compose.
