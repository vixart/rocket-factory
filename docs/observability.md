# Наблюдаемость

Три сигнала идут через один OTel Collector (`deploy/otel/collector.yaml`):

```
Трейсы:  сервис → OTLP → memory_limiter → resource → sampler → batch → Jaeger
Метрики: сервис → OTLP → memory_limiter → resource → batch → Prometheus (remote write)
Логи:    сервис → OTLP → memory_limiter → resource → transform → batch → Elasticsearch
```

Порядок процессоров важен. `memory_limiter` обязан быть **первым** в каждом пайплайне —
он отбрасывает данные до того, как они займут память в других процессорах. `batch` —
**последним**: сначала фильтруем и обогащаем, потом группируем.

Семплирование трейсов — head-based, решение принимается по TraceID, поэтому все спаны одного
трейса гарантированно попадают в одну группу. Локально стоит 100%, в проде обычно 1–10%.

Prometheus работает в push-модели: коллектор сам шлёт метрики через remote write,
а не Prometheus ходит за ними. Поэтому у Prometheus нет scrape-конфига
(`--config.file=/dev/null` и `--web.enable-remote-write-receiver`).

## Логи

`platform/pkg/logger`. slog с fanout-handler'ом: каждая запись дублируется в stdout (JSON)
и в OTLP → Elasticsearch → Kibana.

Две неочевидные детали:

1. **Фильтр уровня для OTLP навешен вручную** (`withMinLevel`). `otelslog.Handler` пропускает
   записи всех уровней, поэтому при `level=info` в Kibana всё равно улетали бы DEBUG-логи,
   которых нет в stdout. Обёртка обязана реализовывать `WithAttrs` и `WithGroup` с возвратом
   такой же обёртки, иначе slog потеряет фильтр при первом же `logger.With(...)`.
2. **Graceful degradation.** Если OTLP-экспортер не поднялся, handler равен nil, и логгер
   остаётся на stdout. Упавший Elasticsearch не роняет сервис.

Внутренняя очередь экспортера ограничена (`MaxQueueSize = 2048`): при переполнении записи
теряются — это осознанный размен в пользу того, чтобы логирование не блокировало приложение.

### Конвенция уровней

| Уровень | Когда | Где |
|---|---|---|
| Info | бизнес-событие свершилось | прикладной сервис |
| Warn | отказ по бизнес-правилу | прикладной сервис, клиенты |
| Error | сбой инфраструктуры или внешнего вызова | границы: клиенты, консьюмеры |
| Debug | шаги сценария, запись в БД, отправка события | репозитории, продюсеры, сценарии |

Правила, которые за этим стоят:

- **Домен не логирует.** Сущности (`inventory/internal/model/entity`) не знают ни про slog, ни про
  контекст запроса. Факт резервирования пишет прикладной сервис, который владеет сценарием.
- **Репозиторий пишет только Debug.** Ошибки он оборачивает и отдаёт наверх; логирует их
  тот, кто превращает их в ответ. Иначе одна ошибка попадает в лог несколько раз.
- **Отказ по бизнес-правилу — это Warn, а не Error.** Нет детали на складе, детали
  несовместимы, неверный пароль, неподходящий статус заказа — сервис исправен, это ожидаемый
  исход. Раньше клиентский `mapErrors` писал Error на любой ответ, включая `NotFound`
  и `Unauthenticated`, и под нагрузкой именно такие записи составляли основную массу «ошибок».
  Теперь уровень выбирается по gRPC-коду (`order/internal/client/grpc/inventory/v1/client.go`):
  бизнес-коды → Warn, `Internal` и ошибки без gRPC-статуса (обрыв связи) → Error.
- **Всегда `*Context`-варианты** (`slog.InfoContext` и т.д.). Без контекста запись теряет
  `trace_id`/`span_id`, и её нельзя связать с остальным запросом.
- **Бизнес-событие пишется после коммита транзакции**, иначе лог соврёт при откате.
- **Никаких дампов структур** вроде `slog.Any("parts", parts)` — это выгружает все поля
  каждой сущности на каждый вызов. Достаточно идентификаторов и счётчиков.

Что не логируется никогда: пароли, bcrypt-хеши, session-uuid (см. [auth.md](auth.md)).

## Трейсы

`platform/pkg/tracing`. Глобальный TracerProvider, `InitTracer` возвращает функцию завершения
(flush + shutdown) — её нужно вызвать при остановке.

Ключевое: явно выставляется глобальный propagator (W3C TraceContext + Baggage). **Без него
каждый сервис создавал бы свой независимый трейс**, и сквозного пути запроса не получилось бы.
Пустые struct'ы у propagator'ов — потому что формат заголовков фиксирован стандартом,
настраивать нечего.

Экспортер: OTLP gRPC, сжатие gzip, retry с экспоненциальным backoff. TLS отключён —
допустимо для локальной разработки и sidecar-коллекторов, в проде нужен `WithTLSCredentials`.

К каждому спану добавляются атрибуты ресурса (имя и версия сервиса, окружение) — по ним
ищут и фильтруют трейсы в UI; детекторы дополнительно собирают данные об инфраструктуре.

## Метрики

`platform/pkg/metrics`. Интервал экспорта — 10 секунд вместо дефолтных 60 у OTel SDK:
на дашборде видно изменения почти сразу, что удобно при локальной разработке и нагрузочных
прогонах.

Бизнес-метрики объявлены как пакетные счётчики (`order/internal/service/order/metrics.go`):
`orders_created`, `orders_paid`, `orders_revenue`. В Prometheus они попадают с суффиксом `_total`.

**Важно про дашборды:** метрики приходят с лейблами инстанса, поэтому при нескольких репликах
запрос без агрегации даёт по ряду на реплику. В панелях Grafana используется
`sum(rate(...[$__rate_interval]))` — именно `sum(rate(...))`, а не `rate(sum(...))`: `rate()`
обрабатывает сброс счётчика отдельно по каждой серии, и при обратном порядке рестарт одной
реплики выглядел бы как обвал общего счётчика.

## Логи в Kibana

Логи лежат в data stream `otel-logs`. Два условия, без которых их не видно:

1. **Index template в Elasticsearch.** Коллектор шлёт логи с `require_data_stream=true`,
   а ES не создаёт data stream автоматически без шаблона и отвечает `index_not_found_exception` —
   логи молча теряются. Шаблон создаёт `task es:create-template`; `number_of_replicas=0`,
   иначе на одноузловом кластере индекс висит в статусе yellow.
2. **Data View в Kibana.** Логи могут быть в ES, а Discover — пустым: без Data View показывать
   нечего. Создаётся `task kibana:create-view` (`otel-logs*`, поле времени `@timestamp`).
   Том Kibana удаляется в `down-core` вместе с saved objects, поэтому view заводится при
   каждом подъёме, а не один раз.

Ожидание готовности Kibana проверяет `status.overall.level == "available"`, а не просто ответ
от `/api/status`: отвечать Kibana начинает раньше, чем поднимет плагины, и в этом окне
`POST /api/data_views` возвращает ошибку.
