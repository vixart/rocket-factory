# Тесты и нагрузка

## Виды тестов

| Что | Где | Чем поднимается |
|---|---|---|
| Unit | `internal/**/tests` | моки от mockery, без внешних зависимостей |
| API | `order/tests/api_test.go` | bufconn-серверы соседних сервисов, реальные Postgres |
| Конкурентность | `order/tests/concurrency_test.go` | те же, плюс подготовка строк напрямую в БД |
| Rate limiter | `order/tests/ratelimit_test.go` | Redis |
| e2e | `order/tests/e2e` | testcontainers: Postgres + Redpanda (Kafka), сборка по тегу `e2e` |

Unit-тесты табличные, с `t.Parallel()`. Моки генерируются `task mocks:gen` по `.mockery.yaml`,
заголовок генерируемых файлов берётся из `.mockery_boilerplate_text.txt` — файл нужен,
на него ссылается конфиг.

## Что проверяет e2e

`order/tests/e2e/setup_test.go` — асинхронная цепочка целиком:

```
HTTP Pay → Kafka order.paid → реальный AssemblyService
         → Kafka assembly.ship-assembled → консьюмер order
         → CommitParts + UPDATE orders SET status = ASSEMBLED
```

В сьюте поднят ещё и IAM (Postgres + Redis + bufconn-сервер), а bufconn-клиент Inventory
снабжён `SessionForwarder`. Причина — сессионная авторизация: HTTP защищён middleware,
gRPC у Inventory — интерцептором, а session-uuid идёт через Kafka-заголовки
(см. [auth.md](auth.md)). Без этой обвязки цепочка обрывается на `Unauthenticated`.

## Фикстуры конкурентных тестов

Тесты, которым нужна деталь с конкретным остатком, **создают собственные строки** прямо
в БД и удаляют их в `t.Cleanup`, а не переиспользуют сидовые. Так тест не зависит от того,
сколько единиц осталось после других тестов.

## Нагрузочный тест

`task load:http` — vegeta, ступенчатый рост 50 → 500 RPS за 2.5 минуты (~41 000 запросов).
Перед прогоном `task load:seed` готовит фикстуры.

Три решения, каждое со своей причиной.

**Детали для нагрузки отдельные, а не сидовые.** UUID с префиксом `10ad7e57` («loadtest»).
Сидовые `550e8400-…` используются API- и e2e-тестами, которые проверяют конкретные цены
и остатки; сброс резерва на них ломал бы чужие фикстуры.

**Фикстуры живут в задаче `load:seed`, а не в миграции.** Это фикстура теста, а не часть
схемы: миграция протащила бы её во все окружения, включая прод, и правка остатка требовала
бы новой миграции. `INSERT ... ON CONFLICT DO UPDATE` делает задачу идемпотентной —
она сама чинит состояние на любой БД, сколько бы прогонов ни прошло до неё.

**Пар деталей несколько (`LOAD_PAIRS`), и vegeta чередует цели.** Каждый успешный Create
резервирует детали через `SELECT ... FOR UPDATE`, поэтому все заказы на одну и ту же пару
выстраиваются в очередь на двух строках — тест мерил бы стоимость блокировки, а не сервис.
Это не теория: на одной паре прогон давал 2 000 успешных заказов и 9 247 ответов 500
(таймауты клиента inventory на ожидании блокировки), на десяти парах — 14 503 успешных
и ноль пятисоток, с упором в rate limiter, как и задумано.

Резерв не освобождается сам, поэтому `load:seed` сбрасывает `reserved` перед каждым прогоном:
иначе N-й прогон упрётся в исчерпанный остаток, order начнёт отдавать 409, а метрика
`orders_created` перестанет расти — в Grafana это выглядит как «график лежит в нуле».

Ожидаемая картина здорового прогона: часть 201, часть 429 от rate limiter, ни одного 409 и 500.
